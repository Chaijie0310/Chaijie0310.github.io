# 订单中心服务重构

> **一句话**：把同时承担下单、履约、对账的单体订单模块，按领域拆成 4 个服务，
> 接口 P99 从 850ms 降到 220ms，大促期间零故障。

## 背景与目标

2023 年初，订单模块已经是公司里最"重"的一块代码：一个 12 万行的单体模块，同时承担下单、
履约状态流转和对账。带来的具体问题是：

- 大促时下单接口 P99 超过 850ms，用户投诉"点了没反应"
- 任何一个小改动都要整模块发布，一次发布的故障影响面是全链路
- 三个小组在同一份代码上并行开发，冲突和回归问题每周都有

**目标**（和 leader 一起定下的口径）：

1. 下单接口 P99 < 300ms
2. 单次发布的影响范围收敛到单个服务
3. 大促期间核心链路零故障

## 技术方案

### 服务怎么拆

按**领域**而不是按技术分层拆：下单（写订单 + 校验）、库存（预占/释放）、履约（状态机）、
对账（T+1 核对）。

- 拆之前先做了 3 周的依赖分析：把模块内的调用关系、事务边界、表访问路径画出来，
  确定哪些表必须同库、哪些可以异步。
- 服务间用 Kafka 做状态流转，查询类走同步 RPC，保证下单主链路只剩 2 次 RPC。

### 性能怎么提

1. **缓存**：热点商品与用户地址进 Redis，命中率 92%
2. **异步化**：对账、通知、积分全部改为消息驱动，主链路去掉 3 次同步写
3. **索引治理**：梳理 17 条慢查询，重写 5 个索引，其中一条报表 SQL 从 8s 降到 60ms

### 被否掉的方案

- ❌ **直接上微服务框架全套**：评估后认为当时团队运维能力跟不上，只拆 4 个服务，
  其余保持模块化单体。
- ❌ **双写迁移**：写放大严重且一致性难保证，最终选**灰度切流 + 影子表校验**。

## 结果

| 指标 | 重构前 | 重构后 |
| --- | --- | --- |
| 下单接口 P99 | 850ms | 220ms |
| 核心链路可用性 | 99.5% | 99.95% |
| 大促故障次数 | 2 次 | 0 次 |
| 单次发布影响面 | 全链路 | 单服务 |

## 复盘

- ✅ **做对的**：先做依赖分析再拆服务，避免了"拆完发现事务跨服务"的返工。
- ✅ **做对的**：灰度切流 + 影子表校验，让迁移期数据问题在测试环境就暴露了。
- 🔧 **会改的**：监控和告警是上线后才补的，应该跟服务一起交付，否则出了问题只能靠日志猜。
- 🔧 **会改的**：服务边界划分时低估了"履约状态机"的复杂度，它后来变成了新的瓶颈。
